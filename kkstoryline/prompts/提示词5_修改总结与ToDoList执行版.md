# 提示词 5 · 修改总结 + ToDoList 执行版（通用模板）

> **使用方法**
> 1. 本提示词在提示词 1–4 任意一个跑完之后使用，属于"执行层"：把改稿建议落地成可勾选的行动清单。
> 2. 把 `{{目标venue}}` 替换成你要投的期刊或会议（如 TIP、CVPR）。
> 3. 需要一并提供给 AI 的材料：
>    - 论文全文（tex / md / pdf 均可）；
>    - 实验代码（如有）；
>    - 之前 AI 生成的全部修改建议（如 `revision_report_full.md`、`storyline_comparison.md`，或直接粘贴之前的分析内容）。
> 4. 从下方分隔线开始整段复制发送。AI 将一次性执行全部阶段，中途不停顿，最后生成交付文件和对比图。

---

你现在是一位 {{目标venue}} 资深审稿人和论文修改执行规划专家（研究方向以我提供的材料为准）。我正在投稿 {{目标venue}}，但论文的故事叙述不行。我已经拿到了一份（或多份）修改建议，现在需要你把"论文原文 + 修改建议"彻底消化，转化为我能直接照着执行的修改方案。

给你足够的时间，不求快，只求吃透和详细。

## 全局执行规则（最高优先级，任何阶段不得违反）

1. **先完整阅读我提供的全部材料：论文全文、代码、每一份修改建议。要求每一句都吃透，完全吃透后再开始解决问题。** 不允许跳读，不允许只看建议标题不看内容。
2. **一次性执行所有阶段，中途禁止停顿、禁止向我提问、禁止等待确认。** 材料有缺失就基于已有内容继续，标注"待验证"。
3. **所有内容不许省略，必须完整输出。** 禁止"篇幅所限""此处从略""详见上文"等任何压缩表述。
4. 全程简体中文；给出的论文替换内容（标题、句式、段落框架）用英文。
5. **禁止编造**：所有判断必须基于我提供的论文和建议材料；材料中没有的实验数字不得出现。
6. **第一部分要通俗易懂、不说废话**：用非专家也能听懂的话讲清楚，每个要点一两句话说透，能用表格和图就不用大段文字。
7. **第二部分要极度详细**：宁可长，不可漏。

## 阶段 0：完整阅读与逐条消化

通读全部材料后，先输出两样东西，证明你已吃透：

1. **论文现状速览**（半页以内）：当前主线一句话、组件与贡献排序、关键实验数字、目标 venue 的核心要求；
2. **修改建议消化表**：把所有修改建议逐条编号，每条填写：

| 编号 | 建议原意（一句话） | 核心思想（为什么要这么改） | 针对论文哪个部分 | 采纳判断 |
|---|---|---|---|---|

- 如果多份建议之间有冲突，明确指出冲突点，给出取舍结论和理由；
- 明显不适合 {{目标venue}} 的建议标注"不采纳"并说明原因。
- 后续两部分输出必须与这张消化表一一对应，不许遗漏任何一条已采纳的建议。

## 第一部分：修改核心思想总结（通俗易懂，提炼重点，不许啰嗦）

### 1.1 一段话总结

用通俗的话（不超过 150 字）告诉我：这次修改的核心思想到底是什么？打个比方也可以。

### 1.2 我现在哪里做得不好

列出问题清单（按严重程度排序），每条只写三句话：

- **问题是什么**（通俗说法）；
- **为什么这是问题**（审稿人看到会怎么想）；
- **改的方向**（一句话）。

### 1.3 改前 vs 改后对比总表

**对比时必须把改前和改后并排放在同一张表里**，至少覆盖以下维度：

| 维度 | 改前（现状） | 改后（目标） | 为什么改后更强 |
|---|---|---|---|
| 标题 | | | |
| 一句话主线 | | | |
| 核心贡献排序 | | | |
| Introduction 逻辑链 | | | |
| Method 组织顺序 | | | |
| 实验叙事逻辑 | | | |
| 图表体系 | | | |
| 审稿人第一印象 | | | |

### 1.4 逻辑结构对比图（直接生成图片）

**直接生成图片文件**，帮我直观理解修改前后的差别：

1. `structure_before.png`：修改前论文的整体逻辑结构图（问题 → 方法组件 → 实验 → 结论的当前串联方式，标出哪里断裂、哪里在抢戏）；
2. `structure_after.png`：修改后论文的整体逻辑结构图（新主线下的因果闭环）；
3. `structure_comparison.png`：把两者并排放在一张图里的对比版（左改前、右改后，用颜色标出变化点：删除的用红、新增的用绿、重定位的用黄）。

生成方式要求：

- 优先用代码直接绘制并保存为 PNG（如 Python + graphviz / matplotlib，注意中文字体，避免乱码；节点文字简短清晰）；
- 若当前环境无法执行代码生成图片，则退而求其次：输出可渲染的 Mermaid 流程图（改前一张、改后一张），并给出我本地把 Mermaid 转成图片的方法；
- 图必须与 1.3 的对比表内容一致，不许图表两套说法。

## 第二部分：超详细修改 ToDoList

### 2.1 总执行次序

先给出全局修改顺序和依赖关系（哪个必须先做、哪个依赖哪个），用编号流程或简单流程图表示。原则：先定主线和贡献，再改标题摘要，再改正文，最后统一图表和交叉引用。

### 2.2 分节 ToDoList

对以下**每一个部分**逐一输出，一个都不能少：**标题、摘要、Introduction、Related Work、Method、实验、结论、图表**。

每个部分按固定格式写：

1. **现状问题**：这部分当前的问题（对应消化表编号）；
2. **目标状态**：改完后这部分应该长什么样（一段话）；
3. **具体步骤**：逐步列出，每一步必须包含：
   - 改哪里（精确到段落/小节/表格编号，能引用原文的引用原文关键句）；
   - 怎么改（具体动作，不许写"优化表述"这种空话；涉及改写的直接给可用的英文句式或段落框架）；
   - 为什么（这一步解决什么问题，对应哪条建议）；
   - 优先级（High / Medium / Low）；
   - 预计工作量（小时级或天级估计）；
   - 完成标准（怎么判断这一步改到位了）。

### 2.3 汇总总表

最后把所有任务汇总成一张可执行总表：

| 编号 | 部分 | 任务 | 优先级 | 依赖任务 | 预计工作量 | 完成标准 |
|---|---|---|---|---|---|---|

并按"第一周 / 第二周 / 投稿前最后检查"给出建议的时间分配（如果任务量不大就按天分配）。

---

## 阶段末：质量自检

输出交付文件前自查并简要声明：

1. 消化表中每条已采纳建议是否都在 ToDoList 中有对应任务；
2. 八个部分（标题、摘要、Introduction、Related Work、Method、实验、结论、图表）是否全部覆盖；
3. 第一部分是否通俗、无废话；第二部分是否每步都有"改哪里、怎么改、为什么、优先级、工作量、完成标准"；
4. 图与对比表是否一致；
5. 是否没有编造论文中不存在的内容。

## 交付文件生成

全部输出完成后，生成以下文件（若当前环境可写文件、执行代码），并告知我每个文件的保存路径：

1. `todolist_report.md` —— 第一部分 + 第二部分的完整内容；
2. `todolist_report.pdf` —— 完整报告的 PDF 版（嵌入中文字体，图片一并嵌入，确保不乱码）；
3. `structure_before.png`、`structure_after.png`、`structure_comparison.png` —— 逻辑结构对比图；
4. `todolist_checklist.md` —— 纯任务勾选清单版（用 `- [ ]` 复选框格式，按执行顺序排列），方便我改一项勾一项。

若环境无法写文件或生成 PDF/图片，则：在回答末尾完整输出全部 md 内容与 Mermaid 图源码，并给出本地一键转 PDF、Mermaid 转图片的具体命令。
