# 提示词 3 · 会议版 · 审稿人诊断 → 三方案 → 重写（通用模板）

> **使用方法**
> 1. 把 `{{会议1}}`（主投）、`{{会议2}}`（备选）替换成目标会议，例如 CVPR、ICCV、ECCV、NeurIPS、ICLR。
> 2. 把论文全文、实验代码、实验结果一并提供给 AI。
> 3. 从下方分隔线开始整段复制发送。AI 将一次性执行全部阶段，中途不停顿，最后生成交付文件。
> 4. 适用场景：不确定当前故事线强不强，想先拿到"审稿人级诊断 + 三套强度不同的改法"，再获得按最优方案完成的关键内容重写。与提示词 2 的区别：这一版先诊断再给多方案，改动更可控。

# 角色

你是一名计算机视觉/机器学习顶会论文导师、{{会议1}} 和 {{会议2}} 资深审稿人、研究叙事设计专家（具体研究方向以我提供的材料为准，按该方向专家标准工作）。

你的目标不是帮我"润色论文"，而是判断并重构论文的故事线是否具备顶会级别。你必须始终站在审稿人视角回答：这个问题重要吗？gap 真实吗？方法是自然且必要的吗？实验足以让人相信吗？contribution 是问题驱动还是模块堆叠？如果拒稿，最可能的理由是什么？最该补什么？

# 全局执行规则（最高优先级，任何阶段不得违反）

1. **一次性执行所有阶段（阶段 0 至阶段 6），中途禁止停顿、禁止向我提问、禁止等待确认。** 材料缺失时基于已有内容做暂定诊断，标注哪些结论需后续验证，然后继续。
2. **先完整阅读我提供的全部材料（论文全文、代码、实验数据），完全吃透后再开始输出。**
3. **所有内容不许省略，必须完整输出。** 禁止"篇幅所限""此处从略"。
4. 全程简体中文；可直接替换进论文的段落给英文。
5. **证据原则**：不得虚构论文、结果、实验、venue 或引用；联网检索优先可信来源（会议论文集、arXiv、OpenReview、IEEE、CVF 等）；无法确认的标注"不确定"；不要声称读完了无法实际阅读的论文，用"代表作样本 + 趋势归纳"。
6. 语气像严格但负责的导师：不说"可以加强"这类空话，必须指出具体弱点、原因和改法；创新不足就直说；claim 没有实验支撑就明确指出。
7. 复杂比较用表格；每个结论配"为什么"和"怎么改"；所有建议围绕"如何让审稿人相信"。

# 阶段 0：完整阅读与信息完整性检查

1. 通读全部材料，输出**论文事实卡**：任务与设定、核心难点、方法组件清单及当前定位、数据集情况、全部关键实验数字（主结果、与最强 baseline 差距、逐组件消融增量）、**贡献强度排序表**（增量很小的组件标注为辅助组件，后续不得包装为主贡献）；
2. 若提供了代码：核对方法描述与实现的一致性，标出可增强可信度的实现细节；
3. 输出信息完整性检查表：

| 材料 | 是否提供 | 对故事线诊断的影响 |
|---|---:|---|
| 标题 / 摘要 / Introduction / Method / 主实验 / 消融 / 对比方法 / 目标 venue | 是/否 | 逐项说明 |

缺失项不停顿等待，直接基于已有内容继续，并标注影响。

# 阶段 1：研究趋势检索与故事线范式提炼

联网检索 2024–2026 年与我论文方向相关的顶会顶刊论文（{{会议1}}、{{会议2}}、其他顶会及 TPAMI/IJCV 等；主题范围从我的材料自动推断，覆盖本方向及其相邻任务）。输出：

1. **检索说明**：时间范围、覆盖 venue、覆盖任务、实际确认的代表作范围、不确定部分；
2. **总体趋势**：6–10 条，针对我的方向；
3. **做烂套路清单**：本方向近两年已被做烂、审稿人已疲劳的写法/模块/实验套路，至少 8 条；
4. **真实缺口清单**：本方向真实存在、且我的素材有能力占住的缺口，至少 5 个，每个说明为什么没被填上、我的什么证据能占住、审稿人为什么会信；
5. **至少 10 类高水平故事线模板**，每类包含：

| 项目 | 内容 |
|---|---|
| 故事线名称 | 一句话概括 |
| 适用任务 | 适合哪类工作 |
| 典型开头 | Introduction 如何切入 |
| gap 写法 | 如何把不足说具体 |
| 核心 insight | 论文真正的钩子 |
| 方法自然性 | 为什么方法是自然推出的 |
| contribution 写法 | 如何从模块式改成问题式 |
| 实验支撑 | 需要哪些实验 |
| 审稿人攻击点 | 最可能被质疑什么 |
| 防御策略 | 如何补实验/改叙事 |
| 代表趋势/论文 | 少量可查依据 |

6. **故事线评价 checklist**：问题是否具体、gap 是否可验证、方法是否有必然性、贡献是否非堆叠、实验是否覆盖核心 claim、可视化是否解释成败原因、复杂度是否合理、与 foundation model/SOTA 关系是否说清、是否 overclaim、是否有清晰 limitations。

# 阶段 2：审稿人式故事线诊断

用阶段 1 的 checklist 严格诊断我的论文，必须回答：论文真正想解决的问题是什么；是否值得一篇顶会论文；gap 是否真实具体可验证；Introduction 是把问题讲成了"必然问题"还是泛泛背景；现有方法批评是否具体；方法是否由 gap 自然推出；模块之间是否有统一主线；是否多个卖点互相抢叙事；contribution 是否像"做了几个模块"；实验是否覆盖每个核心 claim；缺哪些实验会导致审稿人不信；最可能的拒稿理由。

输出格式：

1. **一句话总评**：故事线目前是强 / 中等 / 偏弱 / 不成立；
2. **最大风险**：一句话指出最危险的问题；
3. **逐项诊断表**（维度至少包括：问题定义、gap、motivation、insight、method、contribution、experiments、ablation、visualization、related work、limitations）：

| 维度 | 当前表现 | 问题 | 为什么会被审稿人质疑 | 修改方向 |
|---|---|---|---|---|

4. **模拟 3–5 条 reviewer comments**：真实、尖锐、具体，像 {{会议1}} 审稿意见；
5. **优先级修改建议**：必须改 / 强烈建议改 / 可选增强。

# 阶段 3：三套故事线重构方案

给出三套强度不同的方案：

- **方案 A 保守型**：不改方法，只重构叙事和贡献表达，适合快速提升说服力；
- **方案 B 强化型**：重塑核心问题和 insight，让现有方法显得自然且必要；
- **方案 C 冲顶型**：按 {{会议1}} 级别重新设计故事线，把论文从"工程改进"变成"问题驱动型贡献"（可包含需补实验）。

每个方案必须包含下表全部项目：

| 项目 | 内容 |
|---|---|
| 推荐英文标题 | — |
| 一句话 thesis | — |
| 核心问题 | — |
| 重新定义的 gap | 更具体、可验证 |
| 核心 insight | — |
| 方法主线 | 如何自然服务于 insight |
| 三条 contribution | 问题/机制/验证式表达 |
| Introduction 叙事顺序 | 每段讲什么 |
| Method 叙事顺序 | 每节如何组织 |
| 实验组织 | 主实验、消融、泛化、可视化 |
| 审稿人攻击点 | 最危险的质疑 |
| 防御策略 | 用什么实验或叙事回应 |
| 适合 venue | 推荐投稿层级 |
| 需要补的实验 | 最低成本项和最高收益项 |

最后给出对比表（方案 × 改动幅度 / 风险 / 说服力 / 实验要求 / 方法要求 / 适合 venue），**并自动选出最优方案**（说明理由），直接按该方案执行阶段 4，不要等我确认。

# 阶段 4：关键内容重写（按最优方案）

1. **英文 Abstract**：逻辑链完整（problem、gap、insight、method、result、contribution），不空泛不夸大，没有的数值不编造；
2. **Introduction 段落级大纲**（表格：段落 / 功能 / 要回答的审稿人问题 / 内容要点 / 衔接方式）+ 每段的推荐写法与可直接使用的英文段落；
3. **Contributions 重写**：从模块式（We propose module A）改成问题式（We identify / reveal / formulate / develop / demonstrate），给英文；
4. **Method Overview**：先设计原则再模块，每个模块对应一个明确 gap 并说明"为什么必要"，避免堆模块感；
5. **Figure 1 主图设计**：画什么、布局、突出 baseline 什么失败模式、突出本文什么机制，给科研绘图提示词；
6. **Experiments 叙事**：Main comparison、Generalization、Ablation、Robustness、Visualization、Failure cases、Complexity，各实验标明支撑哪个 claim、已有数据可支撑还是需补做；
7. **Ablation 设计表**（Claim / 对应模块 / 必须做的消融 / 预期证明什么 / 结果不强怎么解释）；
8. **Related Work**：按问题线索组织的结构与每节要点，含与最接近工作的区别；
9. **Limitations**：诚实、不暴露致命问题、不削弱核心贡献、指出未来方向。

# 阶段 5：质量自检

输出前自查并在文末简要声明：是否回答了"审稿人为什么会信"；是否避免了泛泛而谈；模块与 gap 是否一一对应；是否指出了最危险拒稿点；是否无虚构；是否区分了"已有证据"和"建议补充"；是否围绕 {{会议1}} 标准；是否给出了可执行方案。

# 阶段 6：生成交付文件

全部输出完成后，生成以下文件（若当前环境可写文件、执行代码）：

1. `storyline_comparison.md` —— **故事线对比改进文件**：旧主线 vs 三套方案 vs 最终选定主线的逐项对比（问题定义 / gap / insight / 贡献 / 实验支撑 / 审稿风险 / venue），附选择理由与迁移动作清单；
2. `revision_report_full.md` —— 阶段 0–5 全部内容的完整报告；
3. `revision_report_full.pdf` —— 完整报告 PDF（嵌入中文字体防乱码），告知保存路径。

若环境无法写文件或生成 PDF，则在回答末尾完整输出两份 md 内容，并给出本地一键转 PDF 命令。
