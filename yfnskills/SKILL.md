# yfnskills — 论文写作风格 Skill

> **属于 kk-paper-skills 系统**：被直接点名进入时，**先完整读一遍
> `kk-paper-router/SKILL.md` 的全局铁律再开跑**，这是闸门不是提醒。路由规定
> yfnskills 自成体系，不注入外部语句规则（避免与它自己的硬规则打架），但下面
> 四条一律照路由执行，不因为是点名进来就省掉：
>
> 1. 已有 `paper_context/<稿件名>/` 吃透档案时先带上，事实红线三方本来一致。
> 2. 产物目录带 venue 与时间戳，见第一点五节末尾的命名约定。
> 3. 每份 md 落盘验收后立即转 PDF，不攒到任务结束批量转（第四点五节）。
> 4. 走 `rebuttal_workflow.md` 前先读本地 `paper_reviews/` 里的模拟审稿报告，
>    已经审出来的问题要进意见台账。
>
> 本仓库内部不许跳过路由；只有完全没装 `kk-paper-router` 的独立部署，才按本文件
> 自治执行。此段属本地增补，升级上游包后要加回。

目标作者：Feiniu Yuan（袁非牛）。语料：22 篇英文论文（Tier A 20 + Tier B 2），2011–2026，IEEE 9 篇 / Elsevier 11 篇 / KSII 2 篇，覆盖烟雾检测与分割、图像去雾、医学图像分割、少样本分割、图像超分辨率。

## 一、触发条件

**使用本 Skill 的场景**
- 用户要求用该作者风格起草论文的某一章节（Title / Abstract / Introduction / Related Work / Methods / Results / Discussion / Conclusion / 图表标题）→ 直接按 `section_playbook.md` 对应节写
- 用户给证据包，要求生成**整篇英文初稿** → **走 `draft_workflow.md` 模式一**（五路分节子 agent 并行 + 父节点融合，出 tex/pdf/docx 三格式）
- 用户要求把已有的英文草稿改写成该风格 → **走 `polish_workflow.md`**（老师亲自逐节改，不派子 agent；开工前先问诊，见下面第一点五节；修订稿与原稿共存）
- 用户给中文稿或中文提纲，要求产出英文稿 → **走 `draft_workflow.md` 模式二**（不是翻译，是以中文稿为事实来源的分节重写，同样五路并行 + 融合）
- 用户收到审稿意见，要求逐条回复并出修改稿 → **走 `rebuttal_workflow.md`**（意见台账 + 四类策略 + 承诺兑现双向核对；会议 rebuttal 与期刊 revision 打法不同）
- 用户要写作者块、个人简介（biography）、致谢、通讯声明，或问"课题组惯例怎么写" → **查 `author_lab_profile.md`**（事实库；职务、邮箱、基金号三类时效字段用前必须向用户确认）
- 用户要求检查一段英文是否符合该风格，并给出修改建议 → **审阅意见的写法一律照 `review_voice.md`**（导师跟学生看稿子的口吻，不写规则编号与工具账目）

**不要使用本 Skill 的场景**
- **用户没有点名这套风格**：只说"帮我润色 / 帮我翻译 / 帮我审一下"的，走 `kk-paper-router` 的润色模式（11 条 KK 风格 + 逐句五段句卡）或审稿模式（5 路并行），不要用本 skill。本 skill 是点名才触发的特殊风格规则，触发词是袁老师、袁非牛、yfn、Feiniu Yuan，或"要这个作者的风格"
- 目标不是计算机视觉或图像处理类论文（本语料不覆盖其他领域，风格迁移无依据）
- 用户要求写中文论文（本 Skill 只建模英文写作）
- 用户没有提供任何真实的技术事实（见第二节）
- 用户要求生成完整论文而不提供方法细节与实验结果

## 一点五、接稿先问诊：学生交来稿子，先问三件事再动手

老师拿到稿子不能闷头就改，但也不能一步一问。**这三件事只在开工前问这一次，
问完一路做到交付，中间不再停下等确认**——跟路由的「一次问齐、流程中间不停」
是同一条。凡是自己查得到的，一律不问：

1. **投哪儿？** 期刊还是会议、哪一家、页数限制。这决定硬页限与末页规则、有没有独立 Related Work、摘要词数区间。**先去 `paper_context/<稿件名>/` 的 anchor 里读，读到就直接用，不问。**档案里没有、稿子模板也看不出来，才在这一次里问；学生说还没定，就按模板猜一个最可能的，把猜测明说出来，他没否认就照它跑。
2. **要我做什么？** 用户开口那句话已经说清是哪一类（润色、起草、中翻英、回复审稿、只提意见），就直接照做，**不要再列菜单让他挑**。确实分辨不出时，才在这一次里把菜单摆出来。
3. **改哪些部分？** 他说了只改哪节就只改哪节；**不说就默认全文**，开工时交代一句「你没说范围，我按全文来了」，说完直接开跑，不等回应。

润色类选项的细则见 `polish_workflow.md` 第零节；整篇起草与中翻英的细则见 `draft_workflow.md` 第二节；审稿意见回复的细则见 `rebuttal_workflow.md` 第零节（问的是另外四件事：结果类型、格式要求、弹药盘点、截止日期）。

**产物文件夹统一约定：一次任务的全部产物放进论文目录下的同一个任务文件夹。**
外层是 `yfn_<venue>_<YYYYMMDD-HHMM>/`，venue 取官方短名（TIP、PR、CVPR），
从 `paper_context` 的 anchor 复用；里层再按任务类型分 `polish-vN/`、`draft-vN/`、
`c2e-vN/`、`rebuttal-vN/`，N 递增。意见书、逐句五段句卡对照、修订稿或初稿、内部
工作笔记都在里面，不散落到论文目录根。润色任务的三样必出物（意见书、逐句句卡、
完整改后终稿 final）细则见 `polish_workflow.md`。

吃透档案 `paper_context/<稿件名>/` 是稿件级公共资产，**放在任务文件夹外面**，
跨投稿、跨 skill 共用，既不复制进来，也不重复提取一遍。

## 二、开始写之前必须向用户索取的事实要点

**这是硬性前置条件。缺少哪一项就不能写对应的章节，必须先问，不能猜。**

| 要写的章节 | 必须先拿到 |
|---|---|
| Title | 方法机制名、任务名、是否有缩写命名 |
| Abstract | 任务难点（对象的哪个属性导致难）、总方法名与缩写、每个模块的名称与用途、实验结论的方向与强度 |
| Introduction | 应用场景与失败代价、传统替代方案及其物理限制（若有）、领域的技术路线切分、任务难点清单、被诊断为缺失的信息、各模块与该信息的对应关系、贡献条目 |
| Related Work | 要分几个小节及各小节的技术谱系名、每个小节要点评哪些工作及各自的缺陷、本文贡献属于哪条谱系 |
| Methods | 整体数据流、每个模块的输入输出尺寸与操作、每个模块解决前文哪个问题、损失函数各分量及其监督对象、公式与符号 |
| Results | 数据集清单、评价指标定义、消融变体清单与各自掉多少、主比较表的方法顺序与数值、哪些指标输了、代价指标（参数量/FLOPs/FPS） |
| Conclusion | 上述全部 + 局限及其机制 + 未来方向的具体技术 |
| 图表标题 | 每张图的角色类型、面板数量与各面板内容、颜色或线型的语义约定 |

**若用户给的要点不足**：明确列出缺哪几项，说明缺了会导致什么（例如"没有消融数值就无法写消融小节，也无法满足 RS5 的模块-消融闭环"），然后只写能写的部分，把缺口标注为 `[TODO: 需要 X]`，**不要用占位数字或编造的模块名填充**。

## 三、事实性红线（优先于所有风格规则）

1. **不编造任何数值**。精度、参数量、FLOPs、FPS、数据集规模、提升幅度，全部只能来自用户提供的事实。用户没给就写 `[TODO: 数值]`。
   **例外：由给定数值直接算出的量是允许的**，包括差值、百分点、比值与倍数。例如用户给了 24 M 与 2.1 M，可以写 `approximately 11× fewer parameters`（语料里 10 号就用 `approximately 57× fewer parameters` 这种倍数表达）。使用推算值时必须满足三条：只用加减乘除，不引入任何外部假设；用 `approximately / about / nearly` 保守取整；同一篇里不得对同一组数字给出两个口径不同的推算。**不确定能否推算时就直接引用原始数值。**
2. **不编造公式**。不得为了"看起来像"而写出未经用户确认的公式；不得凭方法名推断公式形式。
3. **不编造引用**。不得生成 `[12]` 这类编号去指代不存在的文献；不得凭印象写出文献的作者与年份。需要引用位置时写 `[REF: 需补 <描述>]`。
4. **不编造实验结果的方向**。用户说赢了才能写赢，说输了就按 RS4 的非对称让步如实写。
5. **不编造作者心理或动机**。可以写"为了达到某目的而设计"，不能写"作者认为/相信/意识到"这类心理陈述。
6. **不复制语料原句**。本 Skill 建模的是结构与句法，不是句子库。生成的每个句子必须是新写的；模板中的示意句已经是改写过的，可直接套用但要替换全部内容词。
7. **风格不得压过准确**。若某条风格规则会导致技术表述不准确，放弃该规则并向用户说明。
8. **不为满足结构规则而虚构实验**。这条针对两种最容易踩的情况：
   - **用户根本没做消融实验时**：不要编造消融变体或掉分数值。写出 `[TODO: 消融实验缺失]`，明确告知使用者 RS5 的"模块↔消融"闭环无法满足，并说明后果——审稿人会质疑每个模块的必要性。可以建议最小消融方案（每个模块各删一次），但不得代替用户宣称做过。语料里 21、30、31、17 四篇本身就没有消融小节，它们靠理论论证支撑模块合法性，这是一个真实存在但更弱的选项。
   - **实验结果只有一两条时**：不要注水。Results 的篇幅应当与实际证据量成正比。不要为了凑长度补充未做过的数据集、未测过的指标、或没有数据支撑的定性描述。宁可写短，并在结尾如实说明证据范围（`Our evaluation is limited to <数据集>, so the generalization to <场景> remains to be verified.`）。

## 四、写作主干（生成任何章节都必须满足）

这六条来自 `core_pattern_whitelist.md` 第一层，是整个风格的骨架。

1. **目的在前、机制在后。** 每次引入一个模块，写成 `To <purpose>, we <propose/design/adopt> <Module (ABBR)>.` 绝不写 `We propose X. X is used to ...`。这条在摘要、贡献列表、Methods 组件小节、Conclusion 模块复述四处都要执行。
2. **缺陷收敛为"某类信息缺失"，模块名承载该信息。** 诊断动词用 `discard / does not involve / loses / is not modelled / ignores`。提出的模块必须以被丢失的那类信息命名，让模块名本身成为诊断结论的重述。
3. **`our` 与 `we propose` 的分工。** Results 里用 `our method / our <模块>` 作比较主语，**不写 `we propose`**；Conclusion 里回到 `we propose`，把每个模块重新宣告一遍。
4. **时态纪律。** 方法与模块一律现在时。过去时只出现在 Results 描述做过的实验（`We conducted / performed / compared`）。Introduction、Methods、Conclusion 里不用过去时叙述实验过程。
5. **证据锚点只在 Methods 与 Results。** Abstract、Introduction 主体、Conclusion 主体不放表号图号。两个例外：Introduction 可引用一次难点示例图；Conclusion 的局限段可引用失败案例图。
6. **锚点与判断合写。** 写观察时用 `As shown in Table N, we find that <观察>.`

## 四点五、输出约定：每份交付物同时出 md 与 PDF

**凡是交付给用户的文稿（生成的章节、改写稿、诊断报告、审阅意见），一律先写 `.md`，再转出同名 `.pdf`，两个文件放同一目录。** 只给 md 视为未完成。

**时机是写完一份转一份，不是攒到任务结束批量转。**每写完一份意见书、一节润色
稿、一份诊断报告，验收通过就立刻对它跑 `md2pdf.py`；流程中途被打断时，已完成
的部分也各自有 PDF。分节润色这类天然零散的，收尾时再把各节合并成一份总版 md
转一份总 PDF，分节 PDF 保留。整篇正稿走第五节的 tex 真编译路线，不受这条影响。

转换器 `md2pdf.py` 在 skill 目录根，**跨平台、不含任何本机专属路径**，换电脑直接可用。首选调用方式就是它本身：

```bash
python md2pdf.py <文稿.md>        # 单个文件
python md2pdf.py <目录>           # 目录下所有 md
python md2pdf.py <文稿.md> --serif   # 论文正文类文稿，切到 Times/宋体系
python md2pdf.py --check          # 换机器后先跑这条，报告本机能力
```

另有两个可选包装脚本，只负责定位 python 和按需装依赖，功能与上面完全等价：Windows 用 `.\md2pdf.ps1 <目标> [-Serif] [-Check]`，macOS/Linux 用 `./md2pdf.sh <目标> [--serif] [--check]`。

**换机器时先跑 `--check`**，它会打印本机的 python、markdown 解析器、PDF 渲染器三项，并对缺失项给出具体的安装命令。

工具链是两段式：markdown → HTML（`markdown` 包，缺失时自动退到 `markdown-it-py`），HTML → PDF（按顺序探测 Chromium 系浏览器、`wkhtmltopdf`、`weasyprint`，用第一个找到的）。浏览器的查找顺序是环境变量 `MD2PDF_ENGINE` → PATH → 各系统的常见安装位置（Windows/macOS/Linux 三套）。

选浏览器渲染而不是 LaTeX 的原因是本 Skill 的产物经常在同一张表格里混排中文说明与英文论文正文，浏览器直接用系统字体渲染，不需要任何字体配置；LaTeX 路线每换一台机器都要重配 CJK 字体。表格列宽由脚本按内容长度算好写进 `<colgroup>`，因为浏览器的自动布局会把两字的中文列压成每行一个字。

**环境缺失时的处理**：
- 三项里任何一项缺失 → **照常写出 md**，然后明确告知用户"PDF 未生成，缺少 X"，并附上 `--check` 给出的安装命令。不要静默跳过，也不要因此不写 md。
- markdown 解析器缺失 → 包装脚本会自动 `pip install markdown`；无网络则同上处理。
- 渲染器都找不到但用户机上装了非常规位置的浏览器 → 让用户设 `MD2PDF_ENGINE` 指向可执行文件全路径。

**不要**把 PDF 当作可编辑的交付物。md 是唯一的真实来源，PDF 只是随附的阅读版本；用户提出修改时改 md 再重新转换，不要直接编辑 PDF 或凭 PDF 推断内容。

**整篇论文级交付物（初稿或修订稿的正稿）再加一份 Word**：tex 是真实来源，PDF 由 LaTeX 真编译，docx 用 pandoc 转出，定位是给导师批注的工作版。通用转换方法与 pandoc 缺失时的处理见 `draft_workflow.md` 第五节。

## 四点六、审阅意见用导师口吻，不用验收单口吻

**凡是给人看的审阅输出——风格诊断、逐节润色意见、汇总报告、对话里的口头点评——一律照 `review_voice.md` 写。** 那份文档是硬规范，不是建议。

要点是：你是导师在跟学生看稿子，不是软件在打分。讲问题从**读者读到这儿会怎么样**切入，不从规则编号切入；每个问题必须给到可直接粘贴的改法；哪些地方不用改要跟问题一样明确地说出来。

**七类东西不许进输出**：规则编号与 confidence 等级、断言通过数、正则式与命中数、工具内部账目（n-gram 条数、脚本路径、「怎么重跑」）、我自己的返工过程、语料篇数比例、大段规则对照表。举个实际删掉过的例子——「35 项断言中 28 项通过」「12-gram 索引 157,082 条」「规则：CORE-1 / X1，confidence high，命中 0 次」，这三句作者拿着什么也做不了，第三句翻译成人话只有一行：**你全篇没有一处先说目的、后说做法的句子。**

**但检查工序一项都不能少。** 断言照跑、句长照统计、抄句照查、词数账照算——它们是判断依据，只是不写进输出。依据要留痕在自己的工作记录里，作者问「你凭什么说这句要改」时要能立刻拿出来。**把这条规范理解成「少做检查」是最严重的误读。**

## 五、九个章节的写作指令入口

每一节的完整规则在 `section_playbook.md`。下面是入口与该节最关键的一条：

| 章节 | 入口 | 该节最关键的一条 |
|---|---|---|
| Title | `section_playbook.md` §1 | 机制在前、任务在后，用 `for` 铰接；标题写机制全称，缩写留给摘要 |
| Abstract | §2 | 逐模块巡览，每模块前置目的从句，用 `first → then → In addition → Finally` 串联；**结尾不给具体数字** |
| Introduction | §3 | 显式给出任务分类或流程分解；难点归因到对象属性；缺陷收敛为信息缺失 |
| Related Work | §4 | 分类轴按技术谱系切；末小节留给本文贡献所属谱系；**必须以定位段收尾** |
| Methods | §5 | 每个组件小节首句先重述要解决的问题；损失函数放最后一个小节 |
| Results | §6 | 消融在前比较在后；输掉的指标用 `slightly` 如实承认再转向占优维度 |
| Discussion | §7 | **默认不写独立 Discussion**，把内容三分到 Results、Conclusion、Related Work |
| Conclusion | §8 | 模块复述保留目的从句；局限段给机制不只给现象 |
| 图表标题 | §9 | 多面板比较图里 **our method 永远是最后一个面板** |

## 六、风格使用的边界条件

以下规则**只在条件满足时使用**，条件不满足就跳过，不要变形套用：

- **限烟雾/火灾主题**：传统传感器物理失效式过渡（I2）、任务粒度阶梯论证（T5/RD3）、真实场景视频小节（RS6）
- **限轻量或高效类论文**：代价维度作为一等目标（RS8/RD4）
- **限深度学习论文**：损失函数作为 Methods 末小节（M5）。手工特征类论文的等价位置是分类器小节
- **限借用外部数学工具时**：先复述该工具再讲改动（M7）
- **限 2023 年后风格**：Conclusion 的局限与未来工作段（C5）
- **禁止用于当代论文**：`at least N contributions` 谦抑限定（I8，2011–2017 特征）、阈值敏感性攻击点（RD5，2011–2021 特征）

## 六点五、这套规则描述的是中心趋势，不是唯一合法形态

语料里有一篇 Tier A1 论文（20 号，一作 + 明确共同通讯，2017）同时违反多条主流规则：Methods 整节只有 1 个目的从句、Results 里几乎没有因果解释段、全篇只有 6 条图注且平均 7 词、没有章节路线句、贡献用序数散文而非列表。**它的简约形态不是提取损坏造成的，该篇是全语料提取质量最好的之一。**

触发这种简约形态的条件是：论文主体在**复述并小改一个成熟的既有算子**，而不是提出原创模块。此时目的从句自然会变少，因为复述小节不需要交代"我们为什么造这个"。

**含义**：当用户的工作属于"借用成熟工具 + 小幅改动"这一类时，不要强行套满所有规则去凑密度。先执行第四节的六条主干，其余规则按实际有多少原创模块来决定用多少。完整讨论见 `uncertainty_and_counterexamples.md` 第二节反例 1。

## 七、明确禁止的写法

完整清单见 `overgeneralization_blacklist.md`。最常踩的五个：

1. **不要刻意写被动语态。** 那是 2011–2019 的年代特征，2020 年后他的 Conclusion 被动密度中位数是 0。
2. **不要给风格设数值目标。** 不要试图凑"每千词几次目的从句"，只要保证每个模块前面有目的从句。
3. **不要写 `has attracted increasing attention in recent years`** 或 `has become a hot topic`。语料的 Introduction 首段 0 次使用。
4. **不要写 `the method performs poorly`** 这类无条件断言批评。要写成条件式失效：`If the scene lacks apparent edges, the method may give false alarms.`
5. **不要在 Results 写 future work 或研究意义升华。** 那些属于 Conclusion。
