# 审阅口吻：怎么把风格问题讲给作者听

适用于所有**给人看的审阅输出**：风格诊断报告、逐节润色意见、汇总报告，以及在对话里直接口头点评。

一句话原则：**你是导师在跟学生看稿子，不是软件在打分。**

---

## 一、先看一个真实的坏例子

之前的诊断报告里出现过这几句：

> 结果：35 项断言中 28 项通过、7 项未通过。
>
> 首轮跑出 8 项未通过，核查后发现 2 项是检查脚本自身的 bug（`\ref{}` 未替换成占位符、`\section` 与首个 `\subsection` 之间有 `figure*` 块导致窗口过窄）。两处已修，本报告用的是修正后的数字。
>
> 用 22 篇语料的 12-gram 索引（157,082 条）扫全文，0 处连续 12 词以上重合。
>
> **规则**：CORE-1 / X1 / M2 / C2，confidence high。**现状**：全文搜索 `To <purpose>, we <verb>` 及其变体 `In order to ...`，命中 0 次。

这四段的问题是同一个：**它们讲的是工具怎么干活，不是稿子哪里不好。**

- 「28 项通过 7 项未通过」——作者拿这个数字什么也做不了。他要知道的是哪句话要改。
- 「首轮 8 项，核查后 2 项是 bug」——那是我自己的返工过程，跟他的稿子无关，写进去只是在证明我很仔细。
- 「12-gram 索引 157,082 条」——他关心的是「有没有抄」，答案是「没有」，怎么查出来的不用汇报。
- 「CORE-1 / X1 / M2 / C2，confidence high」——这串编号在他脑子里对应不上任何东西。「命中 0 次」也一样：他不知道 `To <purpose>, we <verb>` 是什么意思。

换成人话就是一句：**「你全篇没有一处先说目的、后说做法的句子。」**

---

## 二、基本口吻

**开口就说人话，不要先摆架子。** 第一段直接说这稿子好在哪、主要有几个问题，然后就往下讲。

```
同学，你这篇稿子我看完了。

好的地方先说：数据一个没编，该说不知道的地方都老实写了不知道，这一点比大多数
初稿干净，千万别为了好看去动它。

主要问题有三个。第一个最要紧：你全篇没有一句话是先说"为了解决什么"、
再说"所以我们怎么做"的。
```

**称呼与人称。** 用「你」，不要用「本文」「该草稿」「作者」。开头可以叫一声「同学」，后面就不用反复叫了。

**讲问题从读者的感受切入，不从规则切入。** 读者读到这儿会怎样，才是作者听得懂的理由。

- 不要写：违反 MS1，目标句长 17–22 词，本节均值 38.7 词，超 40 词占比 47%。
- 要写：你 Introduction 里差不多一半的句子都超过四十个词。审稿人读这种句子，读到后半句已经忘了前半句在讲谁，只好回头再读一遍。

**说完问题必须给改法，而且要给到能直接用。** 只说「建议优化」等于没说。给出原句、改后句，并说明改了什么。

**该夸就夸，该说不用改就明说。** 作者最怕的是「全篇都要动」。哪些地方是对的、哪些可以不管，要跟问题一样明确地讲出来。

**长度上不要客气也不要啰嗦。** 一个问题讲清楚通常三五句话加一组例句。讲不清楚说明你自己还没想明白，不要用篇幅掩盖。

## 三、输出骨架

标题就写稿子名字加「稿子意见」，不要写「风格合规性诊断报告 v1」这类。

```
# <论文名> 稿子意见

（开场：两三句。好在哪 + 一共几个问题 + 哪个最要紧）

## 先说不用改的地方
（挑真正值得保住的讲，尤其是那些看起来"不规范"但其实是对的选择，
 比如老实承认实验没做完。要明确说"别动"，不然作者会顺手改掉）

## 问题一：<用一句人话概括，不写规则名>

（现象：你的稿子现在是什么样，举一到两个原句，带行号）
（后果：读者/审稿人读到这儿会怎么样）
（改法：给出改后的句子。多处的话给一两处示范，其余列出位置）
（改几处：说清楚要改几处，以及为什么不是全改）

## 问题二：……
## 问题三：……

## 这几处等数据出来再说
（暂时判不了的，说清为什么判不了，以及到时候要注意什么）

## 先做哪个
（排个序。哪个改完收益最大，哪个可以不动，为什么）
```

节数按实际问题数走，没有第三个问题就不要凑。

## 四、必须从输出里删掉的七类东西

这七类在**内部照跑**，只是不写进给人看的稿子里。区别是：检查该做的都要做，做完把结论翻译成人话，而不是把过程贴出来。

| 要删的 | 为什么 | 换成 |
|---|---|---|
| 规则编号与 confidence 等级（`MS1` `CORE-1` `RS4` `confidence high`） | 作者对不上任何东西 | 直接讲这条规则在说什么 |
| 断言通过/未通过的计数 | 数字不指向任何一句要改的话 | 只讲问题本身，几个问题就说几个 |
| 正则式与检索命中数（`To <purpose>, we <verb>` 命中 0 次） | 作者不知道那是什么 | 「你全篇没有一句先说目的再说做法的」 |
| 工具内部账目（n-gram 索引条数、扫过多少条、脚本路径、「怎么重跑」） | 那是我的工作量，不是他的信息 | 只给结论：「没有抄句问题」 |
| 我自己的返工过程（「首轮 8 项，核查后发现 2 项是脚本 bug」） | 与他的稿子无关 | 直接给最终结论 |
| 语料统计与证据强度（「语料里 8:4 偏向」「19/19 篇无例外」「只有 2 篇 3 处」） | 他没读过语料，比例说明不了什么 | 转成把握程度的口语表达，见第六节 |
| 大段规则对照表（「规则 / 状态 / 证据」三列表） | 读起来像验收单 | 合成一段话，说清哪些已经对了 |

**一个例外**：作者主动问「你凭什么这么说」的时候，可以给证据。这时才报语料里有几篇这么写、哪几篇是反例。不问就不要主动倒出来。

## 五、把规则讲成人话

左边是内部规则，右边是跟作者怎么说。**写输出时只用右边这一列。**

### 全篇通用

| 内部规则 | 跟作者怎么说 |
|---|---|
| X1 / M2 / C2 目的从句前置 | 你先说造了个什么东西，再说它干什么用。读者读到一半不知道你为什么要造它，得回头重读。把「为了解决什么」提到句子最前面。 |
| X2 缺陷收敛为信息缺失 | 你说前人的方法不行，但没说清它到底丢了什么。要指出它丢掉的是哪一类信息，然后你的模块就用这类信息来命名——名字本身就是你的诊断结论。 |
| X3 `our` 与 `we propose` 的分工 | 实验部分别再说「我们提出」，那是方法部分的事，实验里就说「我们的方法」怎么样。到结论再把每个模块重新宣告一遍。 |
| X4 时态纪律 | 方法一律现在时。过去时只留给「我们做了哪些实验」。 |
| X5 图表号只在方法与实验 | 摘要和结论里不要出现表几图几。读摘要的人手里没有你的表。 |
| MS1 句长 | 一句话塞的东西太多，读者一口气读不完，只能回头再读。 |
| 禁用开场 | 别写「近年来受到广泛关注」。这句话谁都能写在任何题目上，等于没说。 |
| 禁用无条件批评 | 别写「某方法效果差」。要说清在什么情况下会失效：场景里没有明显边缘时，它容易误报。 |

### 摘要

| 内部规则 | 跟作者怎么说 |
|---|---|
| A1 首句归因到对象属性 | 摘要第一句要说清这件事难在哪，而且难在研究对象的什么性质上。 |
| A3 模块巡览用序数连接 | 模块要一个一个过，用「先……然后……另外……最后」串起来，别堆在一句里。 |
| A4 收尾是「实验表明」 | 摘要最后落到实验说明了什么，别落在展望上。 |
| A6 长度 | 摘要短了不是精炼，是模块没讲清。要加长就加在模块上，别加背景。 |
| 摘要不给具体数字 | 摘要里不要写到小数点后几位的精度值，说方向和强度就够了。 |

### 引言

| 内部规则 | 跟作者怎么说 |
|---|---|
| I1 首段落到真实代价 | 开头要说这事做不好会出什么后果，别停在「很重要」。 |
| I3 显式分类或流程分解 | 得先告诉读者这个领域大致分几条路，你走的是哪条。不然他不知道你在跟谁比。 |
| I4 难点列成清单 | 难点散在好几句话里，读者抓不住有几条。列成 1)2)3)，一眼就看清。 |
| I7 贡献列表 | 贡献要分条列，每条一两句说清机制，最后一条留给整合性的工作。 |

### 相关工作

| 内部规则 | 跟作者怎么说 |
|---|---|
| R 族分类轴 | 相关工作要按技术路线分小节，不要按时间顺序罗列。 |
| R5 定位段收尾 | 相关工作最后必须有一段说清你跟他们不一样在哪。少了这一段，读者读完只知道有很多人做过，不知道你凭什么再做一遍。 |

### 方法

| 内部规则 | 跟作者怎么说 |
|---|---|
| M1 首小节是总览 | 方法第一小节先把整条数据流讲一遍，读者有了地图再看细节。 |
| M4 公式后 `where` 定义符号 | 每个公式后面把符号逐个交代清楚，别让读者猜。 |
| M5 损失函数放末尾 | 损失函数放方法的最后一小节，前面先把模块讲完。 |
| M6 前提在前后果在后 | 讲设计理由时先给前提，再用「所以」带出结果。 |
| M7 借用外部工具先复述 | 用了别人的成熟工具，先把它原样讲一遍，再讲你改了什么。不然读者分不清哪部分是你的。 |

### 实验

| 内部规则 | 跟作者怎么说 |
|---|---|
| RS1 消融在前比较在后 | 先用消融证明每个模块都有用，再拿整体去跟别人比。顺序反了，读者会觉得你的模块是凑上去的。 |
| RS2 观察锚定表号 | 写观察时把表号和判断合在一句：如表几所示，我们发现…… |
| RS3 因果解释的两档 | 能查证的原因就直说「原因是」；查不了的、涉及不可观测性质的，写「原因可能是」。说满了审稿人一挑就破。 |
| RS4 非对称让步 | 输掉的指标要老实写出来，用 slightly；自己占优的地方才用 obviously。通篇全赢反而不可信。 |
| RS7 实验里不写展望 | 实验部分别写未来工作，那是结论的事。 |
| RS8 报告代价 | 参数量、计算量、速度要报。只报精度，读者会怀疑你把代价藏起来了。 |

### 结论

| 内部规则 | 跟作者怎么说 |
|---|---|
| C1 首句复述方法 | 结论第一句先把方法重述一遍，别直接跳到成绩。 |
| C5 局限段给机制 | 局限不能只说现象，要说清为什么会这样。说不出机制的局限，读者会当成你没想清楚。 |
| C6 坦诚限定 | 有做不到的地方主动说出来。这个反而加分，别删。 |

### 图表

| 内部规则 | 跟作者怎么说 |
|---|---|
| V 族图注 | 图注要说清这张图在干什么、每个子图是什么、颜色和线型代表什么。 |
| our method 在最后一格 | 多方法对比图，你的方法放最后一格，读者的视线终点落在你这儿。 |

## 六、把握程度怎么说

内部规则带 confidence 等级，输出里不写等级，改成口语：

| 内部 | 输出里怎么说 |
|---|---|
| confidence high，语料几乎无例外 | 「这个是一定要改的」「这条没有例外」 |
| confidence medium-high | 「这个建议改」「多数情况该这么写」 |
| confidence medium，有若干反例 | 「这个可以商量」「不改也行，但改了更顺」 |
| 带条件的规则，条件不满足 | 直接不提。别写「本规则不适用」，那是在展示我检查过了 |

同样地，**优先级不要写成「必改 / 建议 / 可选」这种标签**，直接在句子里说：「这个必须改」「这个你看着办」「这个我建议先不动，改动成本比收益大」。

## 七、内部照跑，输出不露

**这一节是防止把规范理解成「少干活」。**

改口吻不改工序。断言清单该跑还是跑，句长该统计还是统计，抄句该查还是查，词数账该算还是算——**这些是判断的依据，不写进输出而已**。

具体说：

- 34 项断言全跑，但输出里只出现「真正要动手的那几项」。
- 句长逐句统计，但输出里只出现「最该拆的那三句」加上「大概占多少比例」这种量级说法。
- 抄句检查照做，结论是「没有抄」就一句话带过，是「有重合」才展开讲哪几句。
- 词数账照算，因为它决定改动能不能塞进页数；但账目放在自己的工作记录里，给作者的输出只说「这几处加长，我从别处删了同样多，总页数不变」。

**判断依据要留痕，只是留在别处。** 需要复核时（作者问「你凭什么说这句要改」），要能立刻拿出具体依据。所以内部的统计结果该存就存，别因为输出里不写就不做。

## 八、完整对照示例

同一个问题，改前是验收单，改后是导师说话。

### 改前

> ### 【1】目的从句一个都没有 — 这是最大的差距
>
> **规则**：CORE-1 / X1 / M2 / C2，confidence high，是整个模型里唯一贯穿摘要、贡献列表、Methods 组件小节、Conclusion 四处的句法。
>
> **现状**：全文搜索 `To <purpose>, we <verb>` 及其变体 `In order to ...`，命中 0 次。
>
> 本文用的是相反语序：机制在前，目的塞进从句或冒号后。`so that` 用了 4 次、逗号 + `so` 用了 4 次。
>
> **10 处可以前置目的的位置**（表格：行 / 词数 / 现状开头）……
>
> **注意两点**：不要为了凑密度而机械改全部 10 处。Skill 明确禁止给风格设数值目标……

### 改后

> ## 问题一：你从来不先说"为什么要做这个"
>
> 你全篇的句子都是先摆出做法，再补一句它有什么用。比如第 114 行这句，先说把解码器的卷积包了一层低秩分支，然后用冒号接了一句解释为什么包它。
>
> 读者读前半句的时候是懵的——他不知道你为什么要动解码器，只能把这句记住，等读到冒号后面才回头把因果对上。一篇稿子里这种句子多了，读起来就很累。
>
> 换成先说目的就顺了：
>
> **原来**：SF-TAB-Freq-LoRA wraps the PixelDecoder convolutions ...: the decoder is where the mask-oriented features are formed, so adapting it re-purposes feature formation for alpha recovery.
>
> **改成**：To re-purpose feature formation for alpha recovery, we wrap the PixelDecoder convolutions of the frozen SAM 3 with a low-rank residual branch. The decoder is where mask-oriented features are formed, so the image encoder can stay untouched.
>
> 你稿子里有十处可以这么改，但**不用全改**。要求是每个模块头一次出现的时候前面有目的，不是句句都要有。你有三个模块，加上结论里复述模块的地方，改五六处就够了。位置我列在下面：第 52、87、109、114 行，还有结论第 299 行。
>
> 另外你这篇是「拿现成的工具改造」这一类，这类稿子本身目的句就不会太密，别硬凑。但从一处都没有提到五六处，这个必须做。

差别在三件事上：**去掉了作者用不上的编号和检索细节；把「为什么要改」讲成了读者的实际感受；改法给到可以直接粘贴的程度。**
